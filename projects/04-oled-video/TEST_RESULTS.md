# ผลการทดสอบจริง — 7 พฤศจิกายน 2026

## เครื่องมือที่ใช้

- Windows / Python 3.12.14 / FFmpeg 9.0
- PlatformIO Core 6.2.0 / Espressif32 6.10.0
- Arduino ESP32 2.0.17 (`framework-arduinoespressif32 3.20017.241212`)
- RISC-V GCC 8.4.0+2021r2-patch5
- Adafruit SSD1306 2.5.13, GFX 1.11.11, BusIO 1.17.4

Python และ FFmpeg มีอยู่แล้ว ไม่ต้องติดตั้งแพ็กเกจ Python เพิ่ม
PlatformIO ติดตั้งไลบรารีลง environment ของโปรเจกต์สำเร็จ
แก้ตัวแปลงให้ใช้ `-fps_mode passthrough` ซึ่งใช้งานกับ FFmpeg 9.0 ที่ติดตั้งอยู่

## วิดีโอตัวอย่างและข้อมูล Flash

สร้าง `videos/sample.mp4` เองด้วย `tools/make_sample.py`: 256×128, 10 FPS, 5 วินาที
จากนั้นรันตัวแปลงจริงเป็น 128×64, Letterbox, Ordered Dithering

| รายการ | ผล |
| --- | --- |
| จำนวนเฟรม | 50 |
| FPS ที่กำหนด | 10 |
| ระยะเวลาเป้าหมายต่อรอบ | 5 วินาที |
| ขนาดแต่ละเฟรม | 1,024 ไบต์ครบทั้ง 50 เฟรม |
| ข้อมูลภาพรวม | 51,200 ไบต์ |
| SHA256 ข้อมูลภาพที่ pack แล้ว | `e60e0292d34bcdba81de452a751a847c3ed39cef4ec61e2fafa9fa4a5d9beaa4` |

ตรวจ symbol ใน ELF ของโหมดปกติด้วย objdump:

```text
3c030344 l O .flash.rodata 0000c800 _ZL12VIDEO_FRAMES
```

ยืนยันอาร์เรย์ภาพขนาด `0xC800 = 51,200` ไบต์อยู่ใน `.flash.rodata`
ไม่ใช่อาร์เรย์วิดีโอใน RAM สร้าง `videos/preview.gif` โดยถอดข้อมูลจาก header
ที่ pack แล้วจริง และตรวจ SHA256 ตรงกับ metadata

## ผลชุดทดสอบ Python / FFmpeg

`python tools/test_converter.py`: **10 tests ผ่านทั้งหมด**

1. ตำแหน่งพิกเซลอ้างอิงที่มุมและขอบ page: (0,0), (0,7), (127,0), (0,8), (127,63)
2. แถวเต็มและคอลัมน์เต็ม ตรวจตำแหน่ง byte/bit
3. Threshold ที่ขอบ 127/128 และ Invert แบบ bitwise complement
4. Bayer 4×4 ที่เทา 50% ได้ checkerboard และจุดสว่าง 4,096 จุด
5. อ่าน pipe แบบคืนข้อมูลไม่ครบในครั้งเดียว และปฏิเสธเฟรมขาดไบต์
6. แปลง MP4 ตัวอย่าง 50 เฟรม ตรวจทุกเฟรม 1,024 ไบต์และภาพต่างกันตามเวลา
7. Crop/Letterbox บนวิดีโอแนวตั้งสีขาว ตรวจขอบดำและบริเวณภาพตรงตามคาด รวม path มีช่องว่าง
8. แปลง GIF จริง และ MP4 ที่ FPS 2.5: metadata เป็น 5/2 และ 5 เฟรมใน 2 วินาที
9. Flash เกินงบ: มีคำเตือน; strict mode และไฟล์วิดีโอเสียรักษา header เดิม
10. ปฏิเสธ FPS=0, ระยะเวลาติดลบ/NaN, threshold ผิดช่วง และ FFmpeg ที่หาไม่พบ

ตรวจสูตรการจัดบิตเทียบกับ source ของ Adafruit SSD1306 ที่ติดตั้งจริง:
`buffer[x + (y / 8) * WIDTH] |= (1 << (y & 7))`

## ผล Build จริง

คำสั่งหลัก: `pio run -e esp32-c3 -e esp32-c3-usb`

| Environment | I2C | ผล | Flash โปรแกรมรวมภาพ | RAM แบบคงที่ |
| --- | --- | --- | --- | --- |
| esp32-c3 | 400 kHz | SUCCESS | 338,490 / 1,310,720 ไบต์ (25.8%) | 14,376 / 327,680 ไบต์ (4.4%) |
| esp32-c3-usb | 400 kHz | SUCCESS | 324,086 / 1,310,720 ไบต์ (24.7%) | 14,272 / 327,680 ไบต์ (4.4%) |
| test-100khz (ตั้งค่าทดสอบแยก) | 100 kHz | SUCCESS | 338,486 / 1,310,720 ไบต์ (25.8%) | 14,376 / 327,680 ไบต์ (4.4%) |

การทดสอบ 100 kHz ใช้สำเนา ini และ environment แยก จากนั้นนำไฟล์ตั้งค่าทดสอบออก
โปรเจกต์ที่ส่งมอบยังใช้ 400 kHz เป็นค่าเริ่มต้นตามคำขอ
RAM จาก Build เป็นค่า static; ยังมี framebuffer 1,024 ไบต์และหน่วยความจำระบบที่จองขณะทำงาน
พื้นที่แอปไม่เท่ากับ Flash รวม 4 MB และขนาด `.h` ที่เป็นข้อความไม่ใช่ขนาดข้อมูลบนบอร์ด

## พอร์ตและสิ่งที่ยังไม่ได้ทดสอบ

ตรวจรายการพอร์ตโดยไม่เปิด Serial connection พบ COM1 และ **COM4**
COM4 รายงาน `USB Serial Device`, VID:PID `303A:1001` ของ Espressif
ข้อมูลนี้ยังไม่ยืนยันว่าบอร์ดเป็น ESP32-C3 รุ่นเป้าหมายหรือพอร์ตจะไม่เปลี่ยนภายหลัง

**ยังไม่ได้ Upload, เปิด Serial Monitor กับบอร์ด หรือทดสอบภาพ/FPS จริงบน OLED**
ยังไม่ได้จำลอง low-heap บนฮาร์ดแวร์หรือถอดจอเพื่อทดสอบ error path จริง
โค้ดมีการตรวจ OLED ACK และผลการจัดสรร framebuffer แต่ผล Build ไม่ได้ยืนยันฮาร์ดแวร์
ต้องให้ผู้ใช้ยืนยันบอร์ดและพอร์ตก่อน Upload ทุกครั้งสำหรับงานนี้

บันทึกคำสั่งทดสอบอยู่ใน `validation/` (Build ปกติ, Build 100 kHz และชุดทดสอบ Python)
